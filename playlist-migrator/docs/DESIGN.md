# 플레이리스트 이전 서비스 설계서

Spotify · Apple Music · YouTube Music 사이에서 플레이리스트를 그대로 옮겨 주는 웹 서비스.
무료로 제공하고 광고로 수익을 내는 모델을 전제로 한다.

---

## 1. 한 줄 요약

- **제품**: 브라우저에서 A 서비스 로그인 → 플레이리스트 선택 → B 서비스 로그인 → 자동 매칭 후 생성.
- **핵심 난제**: 서비스마다 곡 ID 체계가 다르므로 "같은 곡 찾기(매칭)"가 품질을 결정한다.
- **가장 큰 병목**: YouTube Data API 일일 쿼터(기본 10,000 유닛). 검색 1회 = 100 유닛이라 100곡 플레이리스트 하나로 하루 쿼터가 소진된다.
- **수익 모델**: AdSense 단독으로는 얇다. 광고 + 프리미엄(대용량/동기화) 병행이 현실적이며, 국내 서비스(멜론·지니·벅스·FLO) 지원이 차별화 포인트다.

## 2. 각 플랫폼 API 현황

| 항목 | Spotify | Apple Music | YouTube Music |
|---|---|---|---|
| 공식 API | Web API | Apple Music API + MusicKit JS | **없음** → YouTube Data API v3 사용 |
| 인증 | OAuth 2.0 (PKCE, 브라우저에서 가능) | Developer Token(JWT, 서버 발급) + Music User Token(MusicKit JS) | Google OAuth 2.0 |
| ISRC 제공 | ✅ `external_ids.isrc` | ✅ `attributes.isrc`, ISRC로 검색 가능 | ❌ |
| 플레이리스트 읽기 | `GET /playlists/{id}/tracks` | `GET /me/library/playlists/{id}/tracks` | `playlistItems.list` |
| 플레이리스트 생성/추가 | `POST /users/{id}/playlists`, `POST /playlists/{id}/tracks` (100곡/요청) | `POST /me/library/playlists` (tracks 포함 생성 가능) | `playlists.insert` + `playlistItems.insert` (1곡/요청, 50 유닛) |
| 비용/제한 | 무료. 개발 모드는 사용자 25명 제한 → **Extended Quota Mode 심사** 필요 | Apple Developer Program **연 $99** 필수. 사용자는 Apple Music 구독자여야 함 | 무료. 기본 10,000 유닛/일. 증량은 **API 규정 준수 감사(Audit)** 신청 필요 |
| 주의 | 2024년 말 이후 신규 앱에 일부 엔드포인트 차단(추천, 오디오 특성 등). 검색·플레이리스트는 사용 가능 | API로 라이브러리 곡 **삭제/순서 변경 불가**에 가까움 → "덮어쓰기" 대신 "새 플레이리스트 생성" 방식 | 검색 결과에 뮤직비디오·커버·라이브가 섞임. `videoCategoryId=10`(Music)·`topicId` 필터로 정밀도 보강 |

> 각 플랫폼 개발자 약관·정책은 수시로 바뀌므로 출시 전 최신 문서를 다시 확인할 것.

## 3. 곡 매칭 알고리즘 (제품 품질의 핵심)

### 3.1 매칭 단계

```
1단계  ISRC 정확 일치      (Spotify ↔ Apple Music)           신뢰도 1.0
2단계  정규화 제목+아티스트 검색 후 점수 계산                   신뢰도 0.5~0.95
3단계  점수 < 임계값 → "확인 필요" 목록으로 사용자 검토 유도
```

### 3.2 정규화 규칙

- 소문자화, 유니코드 NFKC 정규화, 기호 제거.
- 괄호/대괄호 안의 `feat.`, `remastered`, `live`, `radio edit`, `deluxe` 등 제거 (단, 비교 시 **버전 태그는 별도 보존**해 라이브↔스튜디오 오매칭 방지).
- 아티스트: `,` `&` `feat.` `with` 기준으로 토큰 분리 후 집합 비교.
- 한국어 곡: 한글 제목과 영문 병기 제목(`"봄날 (Spring Day)"`)을 둘 다 후보로 검색.

### 3.3 점수식

```
score = 0.45 * titleSim
      + 0.35 * artistSim
      + 0.15 * durationSim   (|Δ| ≤ 2초 → 1.0, 10초 이상 → 0)
      + 0.05 * albumSim
- 버전 태그 불일치(live/remix/instrumental 등) 시 0.3 감점
```

- `≥ 0.85` 자동 확정, `0.6 ~ 0.85` 확정하되 검토 목록에 표시, `< 0.6` 미매칭 처리.
- `src/matcher.js` 에 프로토타입 구현 및 `test/matcher.test.js` 에 테스트 케이스가 있다.

### 3.4 YouTube 전용 보정

- 검색 쿼리: `"{title} {artist}"` 한 번만 호출(쿼터 절약). 결과 상위 5개를 점수화.
- 채널명이 `{artist} - Topic` 이면 공식 오디오이므로 +0.1 가산.
- 제목에 `MV`, `Official Video`, `Live`, `Cover`, `Reaction` 포함 시 감점.

## 4. 시스템 아키텍처

### 4.1 원칙: "토큰은 브라우저 밖으로 내보내지 않는다"

Spotify(PKCE), Apple(MusicKit JS), Google(GIS) 모두 **브라우저에서 사용자 인증이 가능**하므로 API 호출을 클라이언트에서 직접 수행한다.
서버는 최소한의 역할만 맡는다. 서버 비용·개인정보 리스크·약관 부담이 모두 줄어든다.

```
┌─────────────── Browser (SPA) ───────────────┐
│  OAuth/PKCE  →  Source API 읽기             │
│  매칭 엔진(Web Worker)  →  Target API 쓰기   │
│  진행률 UI · 검토 UI · 광고 슬롯             │
└──────┬───────────────────────────┬──────────┘
       │ Apple Developer Token 요청 │ 익명 통계/오류 로그
┌──────▼───────────────────────────▼──────────┐
│  Edge/Serverless Backend (Cloudflare Workers │
│  또는 Vercel Functions)                       │
│  - Apple JWT 발급(개인키 보관)                 │
│  - YouTube 쿼터 잔량 브로커                    │
│  - 매칭 캐시 (ISRC ↔ 각 서비스 ID, KV 저장)     │
└──────────────────────────────────────────────┘
```

### 4.2 기술 스택 제안

| 계층 | 선택 | 이유 |
|---|---|---|
| 프론트 | Next.js(App Router) 또는 SvelteKit + TypeScript | SEO 페이지(가이드/블로그)와 SPA 도구를 한 프로젝트에서 처리 |
| 상태/작업 | Web Worker + IndexedDB | 수백 곡 매칭 중 탭 이탈해도 재개 가능 |
| 백엔드 | Cloudflare Workers + KV | 무료 티어가 상업적 사용 허용, 콜드스타트 없음 |
| 캐시 | KV: `isrc → {spotifyId, appleId, ytVideoId}` | 인기곡은 재검색 없이 즉시 매칭 → YouTube 쿼터 절감의 핵심 |
| 분석 | Plausible/Umami(자체 호스팅) 또는 GA4 | 광고 최적화용 트래픽 데이터 |

### 4.3 YouTube 쿼터 전략 (반드시 설계에 포함)

1. **매칭 캐시 우선**: 같은 곡을 다른 사용자가 이미 옮겼다면 검색 없이 캐시 사용. 인기 플레이리스트일수록 적중률이 높다.
2. **쿼터 증량 신청**: 서비스 공개 직후 YouTube API Compliance Audit 제출. 개인정보처리방침·서비스 설명·데모 영상 필요. 수 주 소요.
3. **일일 한도 UI**: 남은 쿼터를 브로커가 관리하고, 소진 시 "내일 이어서 옮기기"를 안내(작업은 IndexedDB에 저장).
4. **비공식 라이브러리(ytmusicapi 등) 사용 금지**: 약관 위반이며 계정 정지·서비스 차단 리스크가 광고 수익보다 크다.

### 4.4 데이터 흐름 (한 번의 이전)

```
[1] 소스 로그인 → 플레이리스트 목록 표시
[2] 선택 → 곡 메타데이터(ISRC, 제목, 아티스트, 앨범, 길이) 추출
[3] 타깃 로그인
[4] 곡별로:  캐시 조회 → ISRC 조회 → 텍스트 검색 → 점수화
[5] 결과 화면: 확정 N곡 / 확인 필요 M곡 / 못 찾음 K곡  (수동 교체 가능)
[6] 타깃에 새 플레이리스트 생성 → 배치 추가
[7] 완료 화면 + 결과 공유 링크(선택) + 캐시 갱신
```

## 5. 수익 모델

### 5.1 광고

- **Google AdSense**: 가장 간단하지만 "도구 사이트는 콘텐츠가 얇다"는 이유로 반려되는 경우가 잦다. 승인율을 높이려면 가이드·FAQ·서비스별 비교 글 등 텍스트 콘텐츠 페이지를 함께 운영해야 한다.
- 매체 RPM(1,000 노출당 수익) 대략치: 글로벌 도구 사이트 $1~5, 한국 트래픽은 그보다 낮은 편.
- 단순 계산: 월 10만 페이지뷰 → 월 $100~500 수준. 광고만으로는 서버비 + Apple 개발자 비용을 겨우 넘기는 정도.
- 광고 위치: 진행률 대기 화면(체류 시간 길어 노출 가치 높음), 결과 화면. 로그인 버튼 옆 등 오클릭 유도 배치는 AdSense 정책 위반.

### 5.2 병행 권장: 프리미엄

기존 경쟁 서비스(TuneMyMusic, Soundiiz, FreeYourMusic)가 모두 같은 구조를 쓴다.

| 무료(광고) | 프리미엄(월 $3~5 또는 1회 결제) |
|---|---|
| 플레이리스트당 200~500곡 | 무제한 |
| 1회 이전 | 주기적 자동 동기화 |
| - | 좋아요/앨범/아티스트 팔로우 이전 |
| - | 광고 제거, CSV 내보내기 |

### 5.3 그 외

- Apple Music 제휴 링크(무료 체험 유도)로 소액 수익 가능. Spotify는 제휴 프로그램이 없다.
- 결제는 Lemon Squeezy / Paddle 같은 MoR(판매자 대행)을 쓰면 국가별 세금 처리 부담이 사라진다.

## 6. 차별화 포인트

1. **국내 서비스 지원(멜론·지니·벅스·FLO·VIBE)**: 공식 API가 없으므로 사용자가 "플레이리스트 텍스트 복사" 또는 "내보내기 화면 캡처/CSV"를 붙여넣는 방식으로 입력받아 매칭. 해외 서비스들이 거의 다루지 않는 영역이라 검색 유입에 유리하다.
2. **매칭 품질 공개**: 확인 필요 곡을 숨기지 않고 보여주며 수동 교체를 지원. 경쟁 서비스의 흔한 불만이 "엉뚱한 곡이 들어감"이다.
3. **개인정보 최소화 메시지**: "토큰은 브라우저에만 저장, 서버에 플레이리스트 저장 안 함"을 전면에 내세운다.

## 7. 법적·정책 체크리스트

- [ ] Spotify Developer Policy 검토 후 Extended Quota Mode 신청 (앱 설명, 스크린샷, 개인정보처리방침 URL 필요)
- [ ] Spotify 브랜드 가이드라인: 로고·명칭 사용 규칙, 메타데이터 장기 캐싱 제한 확인
- [ ] Apple Developer Program 가입, MusicKit 식별자·개인키 발급
- [ ] YouTube API Services 약관 동의, 공개 후 Compliance Audit 제출
- [ ] 개인정보처리방침·이용약관 페이지 (AdSense·OAuth 심사 모두 필수)
- [ ] 각 서비스 로고를 나열하며 "제휴/공식"으로 오인되지 않도록 면책 문구
- [ ] 광고와 음악 서비스 콘텐츠(앨범 아트 등) 병치에 대한 각 플랫폼 정책 확인
